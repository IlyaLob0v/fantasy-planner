# Синхронизация через свой сервер

Статус: **в работе** (2026-10-27): сервер готов, клиент сделан по разделам 1–7, проверка на ПК и телефоне Ильи впереди. Номер версии берётся следующий свободный при слиянии.

## 0. Решения и открытые вопросы

| Тема | Решение |
|---|---|
| Зачем | Илья планирует продавать приложение. Покупатель входит в аккаунт, и герой одинаковый на ПК и телефоне. Яндекс Диск (прежний выбор В6) отменён: покупателю пришлось бы заводить облако и пароль приложения. |
| Принцип | **Local-first.** Приложение, как и раньше, работает на своей SQLite и без интернета. Сервер хранит копию записей и пересылает изменения между устройствами. Правил игры сервер не знает. |
| Сервер | Rust, `axum` + `sqlx` (Postgres), каталог `server/` в этом репозитории, Docker-образ. Сначала тестовый, потом боевой на купленном хостинге, тем же образом. |
| Где тестовый | **На ПК Ильи через Docker** (решение 2026-10-27). Телефон сверяется, когда он в той же сети Wi-Fi и ПК включён. Боевой сервер позже на купленном хостинге тем же образом. |
| Вход | E-mail и пароль. Пароль хранится как Argon2id. Устройство получает токен сессии. |

Открыто до продажи (на сервер сейчас не влияет, но влияет на запуск):

- **С1. Где продаём.** Россия: хранение данных граждан РФ на серверах в РФ (152-ФЗ), оплата через ЮKassa / CloudPayments / RuStore. Весь мир: Stripe / Paddle, Google Play, GDPR. Оба: две площадки оплаты.
- **С2. Как продаём.** Разовая покупка приложения с синхронизацией навсегда (просто, но сервер стоит денег каждый месяц) / бесплатное приложение и подписка на синхронизацию (сервер окупается) / разовая покупка и подписка только на синхронизацию.
- **С3. Шифрование.** Хроника дня — личный дневник. Вариант: шифровать данные на устройстве ключом из пароля (end-to-end), тогда сервер не может прочитать ничего. Плюс к доверию покупателей; минус: забыл пароль — данные на сервере не восстановить, только с устройства.

## 1. Что синхронизируется

Каждая запись летописи имеет ключ, одинаковый на всех устройствах. Связи между записями в пакете идут по ключам, местные `INTEGER id` остаются только внутри устройства.

| Таблица | Ключ записи | Как сливается |
|---|---|---|
| `ledger` | `uid` | **Только добавление.** Запись никогда не меняется, отмена пишется обратной записью. Конфликтов нет: объединение по `uid`. |
| `quests`, `rituals`, `rewards`, `rest_actions`, `inventory` | `uid` | Последняя правка побеждает: запись целиком. Удаление квестов, ритуалов и наград через уже существующий `archived_at`. |
| `ritual_completions` | `uid ритуала` + `_` + `game_date` | Последняя правка. Снятая отметка уходит как удаление. |
| `gear` | `item_key` (предмет каталога есть у героя один раз) | Последняя правка. Отмена находки уходит как удаление. |
| `equipment` | слот | Последняя правка: что надето в слоте. |
| `achievements`, `crest_parts` | `key` | Только добавление. |
| `week_goals` | `week_start`: все цели недели одной записью | Последняя правка набора целей. Если оба устройства без сети поставили цели одной недели, остаётся один набор. |
| `chronicle` | `game_date` | Последняя правка. |
| `saga_chapters` | `key` | Последняя правка: открытие и прочтение главы Сказа. |
| `inn_stays` | `uid` | Последняя правка. Отмена комнаты через `deleted_at`. |
| `quest_steps` | `uid` | Последняя правка; связь с квестом по его `uid`. Удаление пункта через `deleted_at`. Метка `quests.label` идёт вместе с квестом. |
| `days` | `game_date` | Тип дня (`rest`) по последней правке. `deeds_count` и `closed_at` не пересылаются: они пересчитываются на устройстве из `ledger`. |
| `character` | `hero` | Пересылаются только `name` и `location_key` (последняя правка). XP, золото, атрибуты, уровень, серия, «Попутный ветер» и усталость являются кэшем и пересчитываются из `ledger` и `days` после каждой сверки, которая что-то принесла (`src/domain/rebuild.ts`). Счётчик невезения находок остаётся на устройстве. |
| `settings` | `key` | Последняя правка. `motion`, `sound_enabled` и `reminder` остаются на устройстве: анимации, звук и напоминание на телефоне и ПК настраиваются по-разному. |
| `locations` | | Справочник из миграций, не синхронизируется. Открытие локации хранится в `inventory`. |

Почему так: `ledger` уже источник истины для наград. Поэтому дело, сделанное на телефоне без сети, и дело на ПК не затирают друг друга: после сверки оба начисления есть, золото и опыт сходятся.

Правила пересчёта героя (никаких штрафов):

- XP, золото и атрибуты складываются из журнала и не уходят ниже нуля. Если без сети золото потрачено дважды на двух устройствах, долг прощается: золото просто 0.
- Одно и то же достижение и одна и та же цель недели, заработанные без сети на двух устройствах, дают золото один раз.
- Дела дня: живые (не отменённые) записи `quest`, `ritual`, `rest_action` за эти сутки.
- Серия, «Попутный ветер» и усталость получаются повтором подведения итогов по всем дням с первого. Усталость снимается, если после пропуска было дело или сегодня взят отдых.

## 2. Изменения схемы клиента (миграции 0007 и 0013)

- В `quests`, `ledger`, `inventory`, `rest_actions`, `rituals`, `rewards` добавляется `uid TEXT` с уникальным индексом. Старым записям миграция выдаёт `uid`, новым его ставит триггер при вставке, если код его не передал.
- **Журнал исходящих** `sync_outbox(tbl, key, changed_at)`: триггеры на вставку, правку синхронизируемых полей и удаление в каждой таблице из раздела 1 отмечают ключ и время правки. Правка без изменения значения не отмечается, поэтому пересчёт кэша не порождает отправок. `changed_at` служит меткой `updated_at` записи при отправке.
- Таблицы, появившиеся после 0007 (Сказ, таверна, чек-листы, метка квеста), получают такие же триггеры своей миграцией (0013). Новая синхронизируемая таблица или столбец требуют триггеров в новой миграции и записи в `SPECS` в `src-tauri/src/sync/records.rs`.
- `sync_flags.applying`: пока устройство записывает принятое с сервера, триггеры молчат, и принятое не уходит обратно.
- **Ожидающие** `sync_inbox(tbl, key, updated_at, data)`: принятая запись, чья связь ещё не пришла (этап раньше босса), ждёт здесь и применяется, когда связь появится.
- `sync_state` (ключ → значение): адрес сервера, e-mail, имя устройства, `device_id`, токен, курсор, эпоха аккаунта, время последней сверки.

Отправка собирает текущее состояние записи по ключу. Если строки уже нет, уходит отметка удаления `{"_deleted": true}`. При приёме запись применяется, если она новее местной неотправленной правки того же ключа; иначе местная правка уйдёт на сервер и победит там.

## 3. Протокол

Все запросы по HTTPS, тело JSON, токен в `Authorization: Bearer`.

| Запрос | Что делает |
|---|---|
| `POST /v1/auth/register` `{email, password}` | Создаёт аккаунт, возвращает токен. |
| `POST /v1/auth/login` `{email, password, device_name}` | Возвращает токен и `device_id`. |
| `POST /v1/auth/logout` | Отзывает токен этого устройства. |
| `POST /v1/sync/push` `{epoch, changes: [...]}` | Принимает изменения устройства. Каждая запись: `table`, `uid`, `updated_at`, `data`. Сервер сохраняет запись, если она новее хранимой (для `ledger` только если `uid` ещё нет), и даёт ей порядковый номер. |
| `GET /v1/sync/pull?after=N` | Отдаёт записи с номером больше `N`, страницами по 500, новый курсор и эпоху. Свои же записи устройство пропускает. |
| `GET /v1/sync/info` | Эпоха аккаунта и сколько записей в нём: нужно при первом подключении. |
| `POST /v1/sync/replace` | Заменяет летопись аккаунта летописью этого устройства: прежние записи уходят в архив на 30 дней, эпоха растёт на 1. |
| `DELETE /v1/account` | Удаляет аккаунт и все данные на сервере. Нужно для продажи (закон и магазины требуют). |

Сервер хранит записи как непрозрачный JSON: `records(user_id, table, uid, updated_at, device_id, data jsonb, seq bigserial)`. Схема игры на сервере не повторяется, поэтому новые поля и таблицы клиента не требуют правки сервера.

**Эпоха.** Когда другое устройство заменило героя в аккаунте, эпоха растёт. Отправка со старой эпохой отклоняется (409). Устройство со старой эпохой сохраняет свою базу в резервную копию, очищает летопись и принимает героя из аккаунта заново.

Ограничения: тело запроса до 1 МБ, до 1000 записей за отправку, 10 запросов в секунду на токен, пауза в минуту после 5 неудачных входов. `updated_at` строго `YYYY-MM-DDTHH:MM:SS.sssZ`, имя таблицы из строчных латинских букв, цифр и `_`. Удаление аккаунта требует пароль ещё раз.

## 4. Когда идёт синхронизация

- При запуске приложения и при возврате на экран (телефон из фона).
- Через 3 секунды после последнего изменения (квест, ритуал, покупка): одна отправка на серию действий, а не на каждое.
- Кнопкой «Сверить летопись» в уставе.
- Нет сети: изменения копятся локально и уходят при следующей попытке. Игра от этого не зависит ни в чём.

## 5. Первое подключение второго устройства

У Ильи уже два героя: на ПК и на телефоне. Объединять их нельзя: золото и опыт сложатся, а это нечестно. Поэтому при входе на устройстве, где уже есть свой прогресс (есть записи в журнале), а в аккаунте тоже есть летопись, приложение спрашивает один раз:

> «В аккаунте уже есть летопись героя. Какого героя оставить? Местный герой „Илья“ (3 уровень) в любом случае сохранится в файл резервной копии.»

Варианты: «Взять героя из аккаунта» (местная летопись уходит в резервную копию рядом с базой и очищается, герой приходит с сервера) / «Отправить героя с этого устройства» (`/v1/sync/replace`: летопись аккаунта заменяется, её копия остаётся на сервере 30 дней, остальные устройства при следующей сверке принимают этого героя). Без спора выбор делается сам: пустой аккаунт получает героя устройства, пустое устройство получает героя из аккаунта.

## 6. Экран и тексты

В «Уставе гильдии» раздел **«Гильдейская почта»**: вход по e-mail и паролю, имя устройства, время последней сверки, кнопки «Сверить летопись» и «Выйти». В titlebar и на нижней панели ничего не добавляется. Ошибка сети не показывается при каждой попытке: только тихая строка в уставе «Последняя сверка: вчера, 21:40».

## 7. Где что лежит в коде

- `server/`: отдельный Rust-крейт (`axum`, `sqlx` Postgres, `argon2`), свои миграции, `Dockerfile`, `docker-compose.yml` с Postgres для теста. Проверки сервера в CI отдельной задачей.
- Клиент, Rust, `src-tauri/src/sync/`: `records.rs` (сбор записи по ключу и применение принятой, перевод связей `id` ↔ ключ), `client.rs` (HTTP через `reqwest` с rustls), `mod.rs` (команды `sync_status`, `sync_login`, `sync_link`, `sync_now`, `sync_logout`). Правил игры здесь нет.
- Клиент, TS: `src/services/sync.ts` (когда синхронизировать, разбор ответа) и `src/domain/rebuild.ts` (пересчёт героя и дней из `ledger`, покрыт тестами).
- Окно Tauri не обращается к серверу напрямую: CSP не меняется.

## 8. Порядок работ

1. Сервер с тестами (регистрация, вход, push/pull, правила слияния) и Docker-образ.
2. Миграция клиента (`uid`, `updated_at`) и пересчёт героя из `ledger` с тестами.
3. Команды синхронизации в Rust и сервис в TS, экран «Гильдейская почта».
4. Первое подключение второго устройства (раздел 5).
5. Запуск тестового сервера и инструкция для Ильи.
